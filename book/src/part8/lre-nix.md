# Local Remote Execution with Nix

This is the advanced setup: Nix-based toolchains that are bit-for-bit identical between your laptop, CI, and remote workers. Near-perfect cache hit rates. Structural correctness. The full LRE experience.

Local Remote Execution is upstream NativeLink work ([TraceMachina/nativelink](https://github.com/TraceMachina/nativelink)). It is the mechanism that makes a Nix-defined toolchain the same content-addressed data on your laptop, in CI, and on remote workers.

## Prerequisites

- Nix 2.19+ with flakes enabled
- A Docker-compatible container daemon to receive the worker image
- Bazel 7 (LRE toolchain generation and the pinned dev shell target Bazel 7)
- A NativeLink instance (local or remote)

## Step 1: Project Flake

Create `flake.nix` in your project root:

```nix
{
  inputs = {
    nixpkgs = {
      url = "github:nixos/nixpkgs/nixos-unstable";
      # CRITICAL: follow nativelink's nixpkgs for store-path alignment.
      follows = "nativelink/nixpkgs";
    };
    nativelink = {
      url = "github:TraceMachina/nativelink";
    };
    flake-parts.url = "github:hercules-ci/flake-parts";
  };

  outputs = inputs@{ flake-parts, ... }:
    flake-parts.lib.mkFlake { inherit inputs; } {
      systems = [ "x86_64-linux" ];

      imports = [
        # The LRE flake module. It defines the `lre` option namespace, so
        # `config.lre.installationScript` and `config.lre.prefix` exist.
        inputs.nativelink.flakeModules.lre
      ];

      perSystem = { pkgs, config, ... }: {
        devShells.default = pkgs.mkShell {
          packages = with pkgs; [
            bazel_7
            grpcurl
          ];
          shellHook = ''
            # Generate lre.bazelrc with the toolchain paths.
            ${config.lre.installationScript}
          '';
        };
      };
    };
}
```

Two lines carry the whole scheme:

- `follows = "nativelink/nixpkgs"` pins your local Nix packages to the exact nixpkgs NativeLink's worker images use. Same nixpkgs = same store paths = cache hits.
- `imports = [ inputs.nativelink.flakeModules.lre ]` pulls in the LRE flake module (`flake.nix:57` maps `flakeModules.lre` to `local-remote-execution/flake-module.nix`). That module defines the `lre` option namespace (`local-remote-execution/flake-module.nix:12`), which is why `config.lre.installationScript` resolves. The bare `inputs.nativelink.flakeModule` attribute does not exist — the outputs are named `flakeModules.default`, `flakeModules.lre`, `flakeModules.darwin`, and `flakeModules.nixos` (`flake.nix:54-59`). Import `flakeModules.lre` by name.

## Step 2: Enter the Dev Shell

```bash
# If using direnv, it happens automatically:
echo "use flake" > .envrc
direnv allow

# Or manually:
nix develop
```

The shell hook runs `config.lre.installationScript`, which symlinks a generated `lre.bazelrc` into your workspace root (`tools/installation-script.nix:36`). It is a symlink into the Nix store — that is why the header says "do not edit". Here is the actual `lre.bazelrc` the NativeLink repo generates for itself:

```bash
# These flags are dynamically generated by the lre flake module.
#
# Add `try-import %workspace%/lre.bazelrc` to your .bazelrc
# to include these flags to your Bazel environment.

# These are the paths used by your local LRE config. If you get cache misses
# between local and remote execution, double-check these values against the
# toolchain configs in the `@local-remote-execution` repository at the
# commit that you imported in your `MODULE.bazel`.
#
# PATH=/nix/store/<hash>-llvm-binutils-wrapper-22.1.8/bin:/nix/store/<hash>-customClang/bin:...
# CC=/nix/store/<hash>-customClang/bin/customClang
# RUST=/nix/store/<hash>-rust-default-1.93.1:/nix/store/<hash>-rust-default-1.96.0-nightly-2026-03-24

# Bazel-side configuration for LRE.
build:linux --define=EXECUTOR=remote
build:linux --extra_execution_platforms=@local-remote-execution//rust/platforms:x86_64-unknown-linux-gnu,@local-remote-execution//rust/platforms:x86_64-unknown-linux-musl,@local-remote-execution//generated-cc/config:platform
build:linux --action_env=BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN=1
build:linux --extra_toolchains=@local-remote-execution//generated-cc/config:cc-toolchain
build:linux --extra_toolchains=@local-remote-execution//rust:rust-x86_64-linux
build:linux --extra_toolchains=@local-remote-execution//rust:rustfmt-x86_64-linux
build:linux --platforms=@local-remote-execution//rust/platforms:x86_64-unknown-linux-musl
```

Three things about that file are worth calling out:

- The commented `PATH`/`CC`/`RUST` lines are the actual Nix store paths of the toolchain (the real file lists the hashes in full; they are abbreviated to `<hash>` above). They are informational — a fast way to check whether local and remote resolved to the same closure — and evaluating them pulls those store paths into your local Nix store as a side effect (`local-remote-execution/flake-module.nix:64-68`).
- The active flags cover **both** C++ (`generated-cc`) and Rust (`rust:rust-x86_64-linux`, `rust/platforms:...`) toolchains. LRE is not C++-only.
- The `:linux` config prefix appears because the NativeLink flake sets `lre.prefix = "linux"` (`flake.nix:572-575`). A downstream flake that leaves `prefix` at its default empty string gets the same flags as bare `build --...` lines, active for every build with no `--config` (`local-remote-execution/flake-module.nix:201-204`). If you do set a prefix, you must pass `--config=<prefix>` to turn LRE on.

## Step 3: Import LRE in Bazel Config

`.bazelrc`:
```bash
# Import LRE config (only active inside nix develop).
try-import %workspace%/lre.bazelrc

# Remote execution targeting NativeLink.
build --remote_cache=grpc://nativelink.example.com:50051
build --remote_executor=grpc://nativelink.example.com:50051
build --remote_instance_name=main
```

`MODULE.bazel`:
```python
module(name = "my-lre-project", version = "0.0.0")

bazel_dep(name = "rules_cc", version = "0.2.18")
bazel_dep(name = "platforms", version = "1.1.0")

# Import the LRE toolchain module.
bazel_dep(name = "local-remote-execution", version = "0.0.0")
local_path_override(
    module_name = "local-remote-execution",
    path = "./local-remote-execution",  # symlinked from the nativelink repo
)
```

The module is named `local-remote-execution` (`local-remote-execution/MODULE.bazel:5`); `rules_cc 0.2.18` and `platforms 1.1.0` match the versions that module pins (`MODULE.bazel:10,13`).

## Step 4: Build the Worker Image

The LRE worker images are built by Nix as `nix2container` images — not `docker save` tarballs — so `docker load < result` does **not** apply. The flake exposes them as `nativelink-worker-*` packages (`flake.nix:484,488`):

- `nativelink-worker-lre-cc` — the C++ (Clang) toolchain worker
- `nativelink-worker-lre-rs` — the Rust (rustc) toolchain worker

Load one straight into your local container daemon with the image's built-in `copyToDockerDaemon` app:

```bash
# Load the C++ worker image into the local Docker daemon.
# (`nix build .#lre-cc` does NOT exist — lre-cc is a base image, not a flake
#  package; the buildable target is nativelink-worker-lre-cc.)
nix run .#nativelink-worker-lre-cc.copyToDockerDaemon

# The image lands as nativelink-worker-lre-cc:<imageTag>. Capture the tag:
TAG=$(nix eval --raw .#nativelink-worker-lre-cc.imageTag)

# Push to a registry — copyTo writes straight to the destination, skipping
# the local daemon entirely:
nix run .#nativelink-worker-lre-cc.copyTo \
  docker://registry.example.com/nativelink-worker-lre-cc:"$TAG"
```

`copyToDockerDaemon`, `copyTo`, and `copyToRegistry` are the built-in apps every `nix2container` image carries; the worker image is itself a `nix2container.buildImage` (`tools/public/create-worker.nix:80`), and the repo's own tooling drives images the same way (`local-remote-execution/overlays/lre-cc.nix:21`).

The image tag is the Nix derivation hash. Change the toolchain (new Clang version, different flags) and the hash changes, the tag changes, and — because the generated platform config embeds the same hash — the `container-image` platform property changes with it.

**One subtlety that trips people up.** The `container-image` *platform property* the scheduler matches on is **not** the name of the image you deployed. `rbe_configs_gen` writes the generator container name into `generated-cc/config/BUILD`, then a `sed` rewrites it to `lre-cc:<tag>` (`local-remote-execution/overlays/lre-cc.nix:41`). So the property value is `docker://lre-cc:<tag>` even though the container you actually run is `nativelink-worker-lre-cc:<tag>` — a separate extension of the `lre-cc` base image. The property is an opaque string the scheduler matches; the deployed image is chosen independently (`kubernetes/workers/lre-cc/worker-lre-cc.yaml:17-28`).

## Step 5: Configure NativeLink Workers

A worker must run the LRE toolchain and advertise a `container-image` property whose value **exactly** matches the string in the generated platform (`local-remote-execution/generated-cc/config/BUILD:43`):

```json5
workers: [{
  local: {
    worker_api_endpoint: { uri: "grpc://scheduler:50061" },
    cas_fast_slow_store: "WORKER_CAS",
    work_directory: "/tmp/nativelink/work",
    platform_properties: {
      cpu_count: { query_cmd: "nproc" },
      OSFamily: { values: ["Linux"] },
      // Opaque string matched against the platform's exec_properties.
      // Must equal generated-cc/config/BUILD verbatim.
      "container-image": {
        values: ["docker://lre-cc:zms5771rx1yqb4wd6qbj5f9sb2paq75k"],
      },
    },
    additional_environment: {
      // Pass the matched container-image value into the action environment.
      CONTAINER_IMAGE: { property: "container-image" },
      // A per-action scratch dir NativeLink purges afterward. This is a
      // UNIT enum variant, so it is a BARE STRING. `{ action_directory: {} }`
      // is NOT valid: deny_unknown_fields rejects it at load time.
      ACTION_DIRECTORY: "action_directory",
    },
  },
}]
```

The `additional_environment` values are `EnvironmentSource` variants (`nativelink-config/src/cas_server.rs:992`). Two shapes exist, and mixing them up is a common copy-paste failure:

- **Data-carrying variants take a nested object:** `{ property: "container-image" }` (`Property`) and `{ value: "literal" }` (`Value`).
- **Unit variants are bare strings:** `"from_environment"`, `"timeout_millis"`, `"side_channel_file"`, `"action_directory"`. Writing `{ action_directory: {} }` fails with `invalid type: map, expected unit` — the runnable examples under `nativelink-config/examples/` use the bare-string form.

`cpu_count: { query_cmd: "nproc" }` runs `nproc` on the worker and reports the result (`WorkerProperty::QueryCmd`, `cas_server.rs:951`); `{ values: [...] }` is a static list (`WorkerProperty::Values`, `cas_server.rs:947`).

In production the `container-image` value is injected through an environment variable rather than hard-coded, precisely because the tag moves (`kubernetes/components/worker/worker.json5:87-94`):

```json5
"container-image": {
  values: ["${NATIVELINK_WORKER_PLATFORM:-undefined_platform}"],
},
```

The deployment sets `NATIVELINK_WORKER_PLATFORM=docker://lre-cc:$(nix eval --raw .#nativelink-worker-lre-cc.imageTag)` before launching the worker. You can also run the worker directly inside the LRE container with no entrypoint script, since the Nix store paths are already present in the image's filesystem.

> The scheduler must also declare `container-image` (and `lre-rs`, if you run the Rust worker) in its `supported_platform_properties`, or actions requesting those properties never match. Set both to `priority` in the `simple` scheduler.

## Step 6: Build

```bash
# Inside nix develop:
bazel build //...

# First build: actions execute remotely with the LRE toolchain.
# Subsequent builds (same machine or another): cache hits.
```

## The Cache Hit Chain

Why this achieves near-perfect hit rates:

1. **You and CI share the same Nix flake** → same nixpkgs → same Nix store paths
2. **Same Nix store paths** → same toolchain binaries (bit-for-bit)
3. **Same toolchain** → same `container-image` platform property value
4. **Same platform property** → same action hash
5. **Same action hash** → cache hit

If any link in this chain breaks (different nixpkgs, stale flake lock, wrong image), you get cache misses. The fix is always: update the flake lock, re-enter the dev shell, regenerate `lre.bazelrc`.

## Verifying Cache Alignment

```bash
# Check your local toolchain paths:
grep toolchain lre.bazelrc

# Check the remote worker's image:
# (the container-image value in lre.bazelrc's generated platform should match
#  the worker's advertised container-image property)
```

If they match, you get cache hits. If they don't, run:
```bash
nix flake update
# Re-enter the dev shell to regenerate lre.bazelrc.
exit && nix develop
```

## Multi-Language LRE

LRE ships two toolchains, and they do **not** cover the same platforms:

- **C/C++ — `lre-cc`** (Clang from Nix). **`x86_64-linux` only** (`local-remote-execution/flake-module.nix:164`). There is one `lre-cc` image and one `generated-cc` platform.
- **Rust — `lre-rs`** (rustc from Nix). **Multi-platform**: `aarch64`/`x86_64` × `linux-gnu`/`linux-musl`, plus `aarch64`/`x86_64` Darwin (`local-remote-execution/overlays/lre-rs.nix:150-206`). The Darwin targets have *no* container image — they map to a theoretical worker-image tag so bare-metal macOS workers can still advertise exact `exec_properties` (`lre-rs.nix:145-148`).

Because C++ has no Darwin toolchain yet, the flake's `lre.Env` uses only `lre-rs` on Darwin and both toolchains on Linux (`flake.nix:568-571`). A macOS developer gets Rust LRE; C++ actions need a Linux worker.

Each toolchain has its own image and platform property (`container-image` for `lre-cc`, `lre-rs` for the Rust worker). Layer them into one worker or run one worker per language, matched by separate properties.

**Source:** [`local-remote-execution/rust/BUILD.bazel`](https://github.com/TraceMachina/nativelink/blob/main/local-remote-execution/rust/BUILD.bazel)

## Limitations and Workarounds

| Limitation | Workaround |
|-----------|-----------|
| C++ (`lre-cc`) is `x86_64-linux` only | Use `lre-rs` for other platforms, or bare-metal/cross workers |
| No C++ toolchain on Darwin | macOS gets Rust LRE; route C++ actions to a Linux worker |
| Requires Nix | No workaround (Nix is foundational to LRE) |
| nixpkgs must align | Use `follows` in flake.nix religiously, or pin a shared nixpkgs revision |
| Complex initial setup | Follow this guide; once working, maintenance is low |
| Bazel-focused | Buck2 can use the same images but needs manual platform config |

## When LRE is Worth the Complexity

- Teams with 10+ developers (cache sharing saves significant CI time)
- Monorepos with multiple languages (shared Nix closure for all toolchains)
- Organizations where "it works on my machine" is a frequent complaint
- Any team where cache hit rate directly impacts developer velocity
