---
title: Alibaba Cloud OSS
description: Use an OSS bucket as the cache through the S3-compatible API.
---

<Prerequisites>
  A NativeLink development build with the `oss` provider, an OSS bucket, and an
  Alibaba Cloud AccessKey with object read, write, and multipart abort permissions.
</Prerequisites>

The `oss` provider uses the [OSS S3-compatible API](https://www.alibabacloud.com/help/en/oss/developer-reference/use-aws-sdks-to-access-oss)
and the shared NativeLink S3 store. It derives the service endpoint from the
bucket region, uses virtual-hosted addressing, and signs requests with AWS SigV4.
Optional trailing checksums are disabled to avoid `aws-chunked` uploads.
OSS lists the required object and multipart operations in its
[S3 compatibility reference](https://www.alibabacloud.com/help/en/oss/developer-reference/compatibility-with-amazon-s3).
This is an API compatibility basis, not evidence of a successful live deployment.

This provider is available in development builds. It does not migrate objects
from another backend. Object names are `key_prefix` followed by the standard
NativeLink store key, as in the [S3 store](/how-to/stores/s3-and-compatible).

## Configure the store [#configure-the-store]

Configure credentials explicitly for each OSS store. Reference independent
variables such as `OSS_ACCESS_KEY_ID` and `OSS_ACCESS_KEY_SECRET` through shell
expansion. For temporary credentials, also configure `session_token`, for example
`${OSS_SESSION_TOKEN}`. Keep the values out of source control.

There is no fallback to the AWS credential chain or `AWS_*` variables, so an AWS
S3 store in the same process can use its own credentials. Different OSS stores
can reference different variable names. Automatic Alibaba Cloud RAM role
discovery is not supported.

```json5
stores: [
  {
    name: "CAS_MAIN_STORE",
    experimental_cloud_object_store: {
      provider: "oss",
      region: "cn-hangzhou",
      bucket: "example-build-cache",
      access_key_id: "${OSS_ACCESS_KEY_ID}",
      secret_access_key: "${OSS_ACCESS_KEY_SECRET}",
      key_prefix: "cas/",
    },
  },
]
```

Use a separate `key_prefix`, such as `ac/`, for the Action Cache. The optional
`endpoint` overrides the service URL, for example
`https://s3.oss-cn-hangzhou-internal.aliyuncs.com`. It must be HTTPS and must not
contain a bucket, object path, user information, query, or fragment. A native OSS
REST endpoint (`oss-...`) is not interchangeable with an S3-compatible endpoint
(`s3.oss-...`). Bucket-specific CNAME addressing is not supported by this adapter.
Check [OSS endpoint access restrictions](https://www.alibabacloud.com/help/en/oss/developer-reference/use-aws-sdks-to-access-oss)
for the bucket's account and region before deploying.

## Retry and resource behavior [#retry-and-resource-behavior]

The optional `retry` object uses the standard store retry policy. SDK retries
are disabled, but the shared HTTP transport also retries: its attempts can
multiply the store retry loop. There is not yet one total retry budget.

Each SDK operation attempt has a 120-second timeout. The custom HTTP connector
does not currently apply the SDK connection-timeout setting to TCP connections.
Receiving an upload part before an SDK call, reading a download body after the
response headers, and waiting for a consumer are not covered by a total transfer
deadline. These limits need separate validation before production use.

Uploads and downloads use the existing S3 transfer implementation, including
multipart uploads and transfer size validation. Its buffering and concurrency
behavior is inherited. `multipart_max_concurrent_uploads` bounds both queued
parts and concurrent part requests per upload (default: 2). Part sizes depend
on the declared upload size. This adapter does not provide a global byte budget
or upload admission queue. There are no OSS-specific spool, TTL, or read-proxy
settings. To expire cached objects, configure bucket lifecycle rules separately.

## Verify [#verify]

Point the CAS service at this store and run the same build twice with remote
caching enabled. The first build should upload its outputs and the second should
reuse them. Check both a small Action Cache entry and an object large enough to
use multipart upload. A successful replay test does not establish compatibility
with a live bucket, its permissions, or its endpoint restrictions.

<VerifyBlock>
  The second build reports remote cache hits, and downloaded outputs match the
  first build. OSS wire replay tests cover endpoint selection, signing scope,
  direct reads, small uploads, multipart completion, and failure cleanup;
  verification against a real OSS bucket is still required before production use.
</VerifyBlock>
