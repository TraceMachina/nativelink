**Who this is for:** chip, EDA and large-monorepo teams whose build or regression is measured in
thousands of actions and tens of minutes, on hardware that isn't uniform.
**What you'll have at the end:** a clear picture of the pains these builds hit,
how NativeLink answers each one, and where to go next. **Time:** about ten minutes.

NativeLink is a content-addressed build cache and a remote execution service in one
Rust binary, speaking the open Remote Execution API. You run it in your own cloud or
on your own hardware, point your build tool at it, and stop paying for work that has
already been done or that is running on the wrong machine.

## The pains of a chip team's build [#the-pains-of-a-chip-teams-build]

**Verification is the bottleneck, not compile.** The nightly regression is
thousands of simulation seeds and tests, and the slowest of them decide what the
team sees in the morning. Most of that work reruns against blocks nobody touched,
and near the end of the run most of the grid sits idle while a long tail finishes.

**EDA licences are the scarce resource.** A seat costs more than the machine it
runs on. Every rerun of a step whose inputs did not change spends licence-hours
and produces nothing new.

**Flows are scripts around vendor tools.** Make, Tcl and Python glue the steps
together, and the tools read the environment, find files by absolute path, and
write timestamps and hostnames into their outputs. Two runs of the same step rarely
produce identical bytes, which is why caching chip flows has been hard.

**Artifacts are huge.** Netlists, waveform dumps and layout databases are large,
mostly the same from one run to the next, and expensive to move around.

**The grid is mixed and already busy.** On-prem LSF or Slurm, cloud bursting,
GPU boxes for simulation and ML-driven placement. Whatever you add has to fit
alongside what is there.

**IP can't leave.** RTL and layout are the crown jewels, and some of it is
export-controlled. Sending it to someone else's service is not an option.

**Tapeout pressure, and you need to trace the result.** Every hour of regression
or signoff turnaround is felt, and when a result changes the team needs to know
which change produced it.

## How NativeLink answers each one [#how-nativelink-answers-each-one]

| Pain | What NativeLink does |
| --- | --- |
| Verification is the bottleneck | Content-addressed caching skips sims and tests whose inputs did not change, and remote execution runs the rest in parallel across a worker pool. Per-action resource sizing starts the heavy jobs on suitable machines, which helps with the long tail. |
| EDA licences are scarce | NativeLink does not manage licences. A cache hit means the tool never runs, so unchanged work spends no licence-hours. Platform properties route actions only to workers that have the tool and its licence environment. |
| Flows are scripts around vendor tools | Vendor tools cache well once their inputs are declared and their outputs are deterministic. Bazel rules and hermetic toolchains (Local Remote Execution) do the declaring; NativeLink then caches and executes the result. This is the real work of adoption. |
| Huge artifacts | Composable storage: a fast local tier in front of an object store, compression, sharding across backends, and a dedup store that splits files into content-defined chunks so a mostly unchanged file stores and moves only what changed. |
| A mixed, busy grid | NativeLink workers run alongside or inside your existing fleet, on Kubernetes or bare metal, on-prem or in your cloud. One scheduler routes each action by OS, CPU, memory or GPU. NativeLink does not integrate with LSF or Slurm. |
| IP can't leave | You run it yourself, in your own cloud account or datacentre, on storage you configure. It does not phone home, and the source is public so you can audit what runs your builds. |
| Tapeout pressure and traceability | Fewer reruns and more parallelism shorten turnaround. Every action is keyed by the hash of its declared inputs, so identical inputs give identical results and a changed output traces back to a changed input. |

## Your data stays in your infrastructure [#your-data-stays-in-your-infrastructure]

You deploy NativeLink yourself, in your own cloud account or datacentre, on AWS,
GCP, Azure or your own hardware. Your source, build artifacts and cache stay on the
storage you configure. NativeLink does not phone home: it exports telemetry only to
an OpenTelemetry collector you point it at with `NL_OTEL_ENDPOINT`, and sends none
when that variable is unset.

## How it works [#how-it-works]

<Mermaid>
{`flowchart LR
  C["your build tool"] -->|"1 · already built?"| AC["action cache"]
  AC -->|"hit: outputs"| C
  AC -->|"miss"| S["scheduler"]
  S -->|"2 · run this"| W1["worker pool"]
  W1 -->|"3 · outputs"| CAS["CAS"]
  CAS --> C`}
</Mermaid>

Your build tool hashes an action's inputs and asks the action cache whether it has
the result. On a hit the outputs download from the CAS. On a miss the action goes to
the scheduler, which hands it to a worker that matches its requirements, and the
result is stored so nobody runs it again. The CAS, action cache, scheduler and worker
are the same binary started with different configuration.

Caching is the first thing to deploy, and it costs you a URL in a config file.
Remote execution is the step that handles work nobody has done yet, and it is where
large builds gain the most. [Getting started](/getting-started/shared-cache) covers
the cache and [Remote execution](/remote-execution/platform-properties) covers the rest.

## Routing actions to the hardware that fits [#routing-actions-to-the-hardware-that-fits]

The mechanism is **platform properties**: key-value pairs an action declares as
requirements, matched against properties a worker declares about itself. The
scheduler will not assign an action to a worker that does not satisfy them.

<SourceLink file="nativelink-config/src/schedulers.rs" symbol="PropertyType" />

The scheduler declares which keys exist and how each is matched:

**`minimum`** compares numerically: the worker's value must be at least the
action's. It is also **consumable**: an action requesting `cpu_count: 8` subtracts
eight from the worker's available count until it finishes. This is how a 64-core
worker takes eight 8-core actions and not sixty-four.

**`exact`** requires string equality. Use it for OS, ISA, container image or a GPU
model.

**`priority`** only requires that the key be present, and does not restrict by value.

**`ignore`** matches everything, so a client can send a property without it
affecting placement.

<Callout type="warn" title="`priority` is not a constraint">
  A key configured as `priority` will match a worker regardless of the value on
  either side. Use `minimum` for quantities and `exact` for identities.
</Callout>

An unknown property key is refused rather than silently matched: the action stays
queued and the scheduler logs `Unknown platform property`, so a typo stalls visibly.

## GPU-aware scheduling [#gpu-aware-scheduling]

NativeLink routes GPU actions to GPU workers. There is no GPU driver or CUDA
integration in the scheduler; GPUs are first-class in the sense that the scheduler
matches, counts and sizes them through the same property mechanism as everything
else. Three pieces exist.

**1. Route by GPU model or count.** Declare the keys once on the scheduler, and have
GPU workers advertise what they have. The example configurations ship this pair:

```json5
supported_platform_properties: {
  cpu_count: "minimum",
  memory_kb: "minimum",
  gpu_count: "minimum",
  gpu_model: "exact",
}
```

`gpu_count` as `minimum` is both a threshold and consumable, so a worker with four
GPUs holds four single-GPU actions. `gpu_model` as `exact` keeps an action that
needs one device off a different one. A worker states its own values in its
`platform_properties`, so a pool of GPU workers and a pool of CPU workers register
with the same scheduler.

<SourceLink file="nativelink-config/examples/basic_cas.json5" />

**2. Request it per target.** The build asks for a GPU the way it asks for any
platform property, for example a Bazel `exec_properties = {"gpu": "a100"}` on the
target that needs it. Targets that request nothing still match every worker. If no
worker matches, the action waits and the scheduler logs which key had no candidate,
for example `No candidate workers due to a lack of matching 'gpu' = Exact("a100")`.
The [platform properties](/remote-execution/platform-properties) page has a worked
GPU pool example.

**3. Scheduler hints for GPU sizing.** <MinVersion v="1.8.7" /> The `historical_resource` scheduler applies
resource hints before handing the action to the nested scheduler. Its size classes
can name `gpu_count` and `gpu_memory_kb`, so a class stands for a whole device or a
slice of one. Class rules (`class_by_mnemonic`, `class_by_timeout`, `default_class`)
supply the GPU share for untagged actions. Device memory can also be learned: a
wrapper around the action reports `peak_gpu_memory_kb` in the worker's side channel
file, the scheduler keeps the observed peak, and it offers the action only to
workers advertising that much. A share of a device is always stated, never measured.
See [scheduler internals](/explanations/scheduler-internals).

<SourceLink file="nativelink-config/src/schedulers.rs" symbol="SizeClassSpec" />

<Callout type="info" title="What NativeLink does not do">
  A worker does not discover GPUs by itself. You declare `gpu_count`, `gpu_model` and
  device memory in worker configuration (a `query_cmd` can compute a value at
  startup), and whatever wraps your action reports device memory use. The scheduler
  trusts what workers advertise.
</Callout>

<Callout type="warn" title="One shipped example gets this wrong">
  `kubernetes/nativelink/nativelink-config.json5` declares both `gpu_count` and
  `gpu_model` as `priority`, which enforces nothing: an action asking for four GPUs
  can land on a worker with none. If you started from that file, change both to
  `minimum` and `exact`.
</Callout>

The same pattern covers everything else that varies. `os` and `arch` as `exact` give
cross-platform pools from one scheduler. A key such as `vendor_tool` as `exact`
keeps an action on workers that have that tool installed and can reach its licence
server. You define these keys; NativeLink only matches them.

## Running a heterogeneous fleet [#running-a-heterogeneous-fleet]

<Mermaid>
{`flowchart TB
  S["scheduler<br/>declares which keys exist<br/>and how each is matched"]
  S -->|"cpu_count ≥ 4"| C["compile pool<br/>many small workers"]
  S -->|"memory_kb ≥ 64000000"| L["link pool<br/>few large-memory workers"]
  S -->|"gpu_count ≥ 1<br/>gpu_model = a100"| G["GPU pool"]
  S -->|"os = windows"| O["platform pool"]`}
</Mermaid>

One scheduler serves every pool. Each worker announces what it is and the scheduler
routes on that. Start with one pool and split it only when you can name the reason.
[Run multiple workers](/how-to/run-multiple-workers) is the mechanics and
[tuning](/operate/tuning) covers sizing.

## Toolchains and provenance [#toolchains-and-provenance]

The routing is the straightforward half. The half that takes the time is making
actions hermetic enough to run somewhere else: a compiler at an absolute path, a tool
the platform team installed years ago, a license daemon. Declaring those assumptions
is the work, and it is also what gives you determinism and provenance, because an
action whose inputs are all declared and hashed has the same digest every time.

**Local Remote Execution** builds the toolchain itself as a declared, reproducible
artifact, so your local build and your remote workers use the same toolchain and
share one cache. See [Local Remote Execution](/explanations/lre) and
[Toolchains and hermeticity](/remote-execution/toolchains-and-hermeticity).

Plan remote execution as a toolchain project, not a config change. That is how these
migrations avoid stalling.

## Proof points [#proof-points]

- NativeLink is in production for customers including large corporations such as
  Samsung, handling over ten billion requests a month (nativelink.com).
- One published account, Reid Kleckner's, builds LLVM with `recc` executing remotely
  against NativeLink and takes a build from roughly seventeen minutes to roughly
  four. It is one person's measurement on their own hardware, with caveats the post
  spells out, so treat it as the shape of the result, not a number to plan against.
- Speedups on this class of build vary widely, because they depend on how wide the
  graph is, how long the critical path is, and how much was already cacheable.
  Measure your own.

## Common questions [#common-questions]

<Accordions>

<Accordion title="My build is CMake or Make, not Bazel. Is any of this available?" id="my-build-is-cmake-or-make-not-bazel-is-any-of-this-available">

Partly. `recc` puts a CMake-based build on the remote cache by intercepting
compiler invocations, and it's the documented path for large C++ trees. The setup in
these docs is cache-only (`RECC_CACHE_ONLY=1`, so misses compile locally). Remote
execution of the whole graph needs a build tool that describes every action's
complete input set, which is what Bazel, Buck2, Siso and BuildStream do and Make does
not.

</Accordion>

<Accordion title="How do I stop huge link actions from crowding out compiles?" id="how-do-i-stop-huge-link-actions-from-crowding-out-compiles">

Give them different properties and let `minimum` do the accounting. A link action
declaring a large `memory_kb` only matches workers that have it, and because
`minimum` is consumable, one such action holds that worker's memory budget until it
finishes. If they still collide, split the pool.

</Accordion>

<Accordion title="Can workers run different operating systems?" id="can-workers-run-different-operating-systems">

Yes. Declare `os` as `exact` on the scheduler, have each worker declare its own, and
one scheduler routes to all of them. The action's toolchain has to exist for the
target platform.

</Accordion>

<Accordion title="Does a vendor tool's license server work with this?" id="does-a-vendor-tools-license-server-work-with-this">

Yes, unchanged. The tool still checks out a seat from the licence server as it
always did, so the worker needs network access to it. NativeLink does not track or
allocate seats. Two things help: a cache hit means the tool never runs, so no seat
is used, and a platform property can keep the action on workers set up for that
tool. A consumable `minimum` key can cap how many such actions run at once on one
worker, but that is a per-worker count, not a fleet-wide seat pool.

</Accordion>

<Accordion title="Is the cache still worth it if most of my actions are unique?" id="is-the-cache-still-worth-it-if-most-of-my-actions-are-unique">

Usually yes. Third-party dependencies, the toolchain and everything below your change
are shared. For workloads that are new every run, such as some ML training and
fuzzing, remote execution is the part that helps.

</Accordion>

</Accordions>
